## 二、Function Calling 诞生的背景

大模型刚诞生的那一两年，所有聊天大模型都只会说话，**没有任何工具调用能力**。这带来两个问题：

1. **无法感知环境**：没法帮你查网页、看本地文件、访问公司远程部署的数据库等。
2. **无法改变环境**：没法执行代码或做任何实际操作。

而这一整套能力恰恰是**传统后端**擅长的，并且很多大模型都提供了可供后端接入的 SDK 或 API。所以思路是：把两者结合，让后端去做工具调用操作。

### 初步方案（后端硬编码）

以"广州今天的天气如何"为例：

1. 请求到达 AI 应用程序后端时，先做判断处理——需要调用一个查天气的方法。
2. 后端通过**正则**匹配用户提问里的关键词（如"天气"），判断是否需要调用天气方法。
3. 再通过**字符串匹配**等拿到要查的城市/地点（比如后端维护一个城市表，看有没有命中其中词条）。
4. 拿参数去调用写死在 AI 应用本地的方法（即便调 API，也还是得在本地发起 HTTP 请求、解析响应，最终仍是调本地方法）。
5. 拿到天气信息后，把它连同原始用户输入和其他上下文（历史对话）一起发给大模型。
6. 大模型有了足够信息，返回最终结果："广州今天 35 度"。

### AI 应用程序层非常重要

一定要弄清楚：**用户的提问不是直接到达大模型的**。就算你在网页上用 ChatGPT 聊天，它也是一个完整的前后端应用，提问先经过后端，后端再去调用大模型暴露出来的接口（该接口帮你实现大模型底层能力）。

### 初步方案的两个问题

1. **正则判断易误判**：逻辑复杂、容易漏判。比如只正则"天气"关键词，用户问"广州今天下不下雨"就会漏判。
2. **参数提取易出错**：参数和用户输入强相关，用字符串匹配（如城市表命中）容易出错。比如用户问"我今天要去中山大学，帮我看看天气"，可能给你查成"中山"的天气。

## 三、Function Calling 方案

### 核心思想

这两个问题的本质是**对自然语言的的理解**，这种事情应该交给"智能的东西"去做，不该交给后端 hard-code。于是引出 function calling：

> 既然大模型这么智能但什么都做不了，而后端能做很多事情，那么**能不能让大模型去告诉后端它要做什么，由后端去完成方法调用并返回结果**？

**广义的 function calling**：指能够让大模型调用外部工具的这类技术实现。

### 流程

1. 先向大模型传递**当前拥有的所有方法列表及详细说明**：每个方法是干什么的（如 `get_weather` 查天气）、每个参数的类型和含义。
2. 把这个列表和用户输入一起传给大模型，让它自己判断是否需要调用函数。
3. 若需要，让它自动生成调用所需参数，最终返回一个**规定格式的函数调用请求**。
4. 既然格式是规定的，后端就能**标准化解析**该请求，完成方法的实际执行。
5. 这就变相实现了"让大模型调用外部方法"。

### 传递函数描述的两种方式

关键问题是：怎么把可用函数列表（后面叫**函数描述**）传给大模型？有两种方式：

1. 通过**提示词**传递；
2. 在 **API 中新增一个参数**允许传递。

## 四、基于提示词的 function calling

### 流程

1. 用户发起提问"广州天气如何"，请求到达你开发的 AI 应用后端（比如一个数字人、AI 助手）。
2. 后端向大模型 API 发起调用，带上一个 **system prompt**，大意是：
   - "你是一个函数调用助手，我会给你提供很多信息。你的任务是根据用户输入判断是否需要调用函数；如果调用，必须按这个格式给我调用指令。"
   - 提示词里带上所有函数的说明。
3. system prompt + 用户提问一起传给大模型，若一切符合预期，它返回一个调用指令，例如：函数名 `get_weather`，arguments 里第一个参数 `city = 广州`。
4. 后端解析指令，完成实际方法调用：可通过**反射**实现，或维护一个 map（key 是方法名，value 是一个 function）。不管怎样，调用的都是写在 AI 应用内部的本地方法。

### 这种方式的问题

1. **模型能力本身**：
   - 输出格式可能不稳定，不遵循指令，比如返回一句自然语言"好的，我已经给你生成了想要的结果"。
   - 可能出现**幻觉**，调用的函数并不在你的方法列表里。
   - 解决办法：提升模型能力——由大模型提供商针对这方面做微调或强化学习训练。
2. **对开发者依赖程度高**：调用指令格式、函数描述格式都由开发者自己设计，自由度高。不熟悉大模型的开发者，提示词效果可能很差。解决办法：由大模型提供商在系统内部兜底，写好 function calling 的提示词。
3. **成本高**：每次都要传 system prompt，且为保证逻辑正确还要附加大量约束说明，企业成本上升。

这些问题的存在，催生了更先进的方案——**狭义的 function calling**。

## 五、狭义的 function calling

狭义 function calling 特指：**大模型提供商在模型内部和 API 层面做了特别支持的能力**，最早由 **OpenAI** 引入。包含两层：

### 1. 模型层面

为解决格式不稳和幻觉问题，提供商需对大模型做特别优化，使其能正确选择合适方法、生成有效且正确的参数。可通过 **SFT（监督微调）** 或**强化学习**等方式实现。

### 2. API 层面（更重要）

提供商必须在 API 层做支持——"它不做，你就直接用不了"。例如 GPT 开放 function calling 时，在调用 API 中增加了 `functions` 参数：

- 把所有函数描述塞进这个参数里；
- 不用自己写系统提示词，内部已做好规范；
- 返回的调用指令按提供商约定的格式，你只要按规定解析即可。

### 工作流程

1. 用户提问到达 AI 应用后端。
2. 后端不必写任何 system prompt（想写也行），把所有函数描述放进调用接口的 `functions` 参数里。该参数是一个列表，大致长这样：
   - 一个 JSON 对应一个方法；
   - 第一个方法：`get_weather`，`description` 是"获取指定城市的天气"；
   - 还有参数描述，包括参数类型、解释，以及是否必填。
3. **重要**：传入的函数描述（方法列表）格式必须遵循所调用那家大模型 API 的标准化要求，不能自己乱写。
4. 把方法列表丢进 `functions` 参数，把用户原始输入丢进 `user message`。
5. 大模型返回一个标准化格式的调用指令（格式也由提供商规定，不用自己操心）。
6. 后端解析指令，通过反射等方式调用本地方法；拿到结果后**第二次向大模型发起请求**，得到最终回复。

### 狭义方案的问题

1. **切换模型的冗余开发**：正常开发者都希望用户能在前端自由切换大模型。但每家 API 的函数描述格式、返回的调用指令格式都完全不一样，接一个新模型就要重新适配一套。
2. **致命问题**：你永远没法推动所有大模型提供商都投入人力成本来给你搞这套支持，所以最终能用的模型非常有限。

## 六、MCP 协议要解决的是另一件事

**明确一点**：MCP 协议**不是**为了解决上面第四、第五节那些（提示词 / 狭义 function calling）的缺陷，它解决的是完全不同的事情。

在 function calling 流程里，不管哪种方式，最终返回的都只是一个**规范化的调用指令**；**方法的实际执行永远在 AI 应用后端自己实现**。由此带来问题：

1. **工具接入存在大量冗余开发**：你本地写好了一个 `get_weather`（内部做了 API 鉴权、调 API、解析结果），现在想给另一个 AI 应用接入，或接入别人写的类似方法，就得**完整 copy 这个方法及其函数描述**。想接几个就 copy 几次，很繁琐。
2. **工具复用困难（致命）**：copy 来的代码可能因环境、依赖问题跑不起来。
3. **企业不愿公布源码**：很多企业/团队愿意对外提供能力，但不愿随意公布源码，也就是不给你代码 copy。
4. **跨语言代码**：这个真的 copy 也没用。

如何做到"能用别人的方法，但不用 copy 别人的代码"？

---

## 七、从问题出发：两个思路

现实中已有成熟做法可借鉴：**import 别人的包本地调用**，或**直接调别人暴露的 API**，这样不用关心内部实现语言和运行环境。

分析可行性：

- **import 包**：不太好解决跨语言问题；企业不愿提供源码时也麻烦。
- 但"跨语言"和"不愿提供源码"这两个子问题并非绝对无解：
  - **跨语言**：拉代码到本地后虽不能直接本地调用，但电脑/服务器通常有多语言执行环境。可以**在本地另起一个进程去执行对应语言的代码**，AI 应用后端再通过**进程间通信**获取标准化的返回结果。
  - 进程间通信方式有很多：匿名管道、有名管道、消息队列、共享内存、信号量等，具体选用可后续再定。
- **不愿提供源码**：作者后来看了 MCP 的一些包，发现企业提供的包很多直接打包成一个 **EXE 可执行文件**，根据你的操作系统判断执行哪个 EXE，根本不让你看源码。

于是思路一可行，而且这种接入方式更准确的说法不是"导包"，而是**起一个本地服务**，通过进程间通信的方式做**本地服务式接入**。

**思路二**就简单了：把工具**远程部署**，封装成标准化 API，约定好请求响应格式去调用——即**远程服务式接入**。

从问题出发，得到了这两个思路。

---

## 八、从目标出发：理想状态与技术需求

### 理想状态

对开发者来说，接入工具最理想的方式是：**加一条配置就能接一个新工具，其他什么都不用改**。

### 现状与打通条件

现状链路：每新增一个工具，开发者要在 AI 应用后端补充工具代码，还要在配置文件/数据库里补充新的工具描述。

从非理想到理想，需要满足：

1. 新增配置后，AI 应用后端如何**根据配置自动获取工具的描述信息**；
2. 新增配置后，AI 后端如何**根据配置自动找到工具调用入口并执行调用、拿到反馈结果**。

由此把最初的困难转换成具体的技术需求。

### 技术需求（两个思路都要实现）

两个思路覆盖的东西并不完全重叠：如果想调用本地服务（如本地操作系统接口），用远程 API 无法实现。所以要做到"完美解决工具接入和复用困难，无论本地工具还是远程服务"，**两种思路最终都得实现**，否则接入工具有局限性。

- **本地服务式接入**：在任意 AI 应用中，只需一条标准化配置，就能把任意工具开发者提供的包拉到本地，并在本地起一个进程把工具作为 server 启动；还要能通过一条配置自动获取工具描述、自动完成调用。这需要实现**本地进程间通信**。
- **远程服务式接入**：在任意 AI 应用中，通过一条标准化配置就能访问任意工具服务，并能自动拉取工具描述；模型返回标准调用指令后，自动完成整个调用过程。这需要实现**远程服务调用的标准化**。

## 九、技术方案与架构设计

### 大前提

1. **AI 应用与工具必须解耦**：无论本地还是远程接入，工具都是作为一个服务给 AI 应用提供能力。
2. **交互必须标准化**：要做到那么多"任意"和"自动"，工具服务与 AI 应用后端之间的所有交互都必须标准化。

### 需要标准化的内容

沿着调用链路拆分，需要统一四件事：

1. **通信协议**：AI 应用与工具服务之间的通信协议得统一。比如工具给的是 Socket 接口，而 AI 应用全走 HTTP，根本调不通。
2. **工具服务至少要做两件事**：
   - 提供自身的**描述信息**（用来拼接 `functions` 入参）；
   - 真正**执行自己的方法**并返回结果。
   - 还要细分确定接口里包含哪些参数、参数什么格式。
3. **数据交换格式统一**：调接口的方式（是固定 URL 拼不同 path，还是同一个 URL 用请求体区分）、响应的格式都必须统一。
4. **配置内容本身标准化**：不能两个工具服务提供两种配置，让 AI 后端做各种兼容——否则配置搞出七八十种、上百种格式，生态无从谈起，大家又各玩各的。

后两条更偏向**约束开发者行为**：

- 工具服务开发者：严格遵循协议开发，保证暴露出来的配置"一配就能调"；
- AI 应用开发者：在后端实现标准化逻辑——解析标准化配置、执行对应方法、加载工具、获取工具描述、在合适时机自动完成调用。

### 架构设计图

- AI 应用后端与工具服务**解耦**。
- 工具作为服务独立部署，**一个服务提供一组工具**（实现某一类功能），而不是一个服务只提供一个方法。例：本地的 tool server 提供处理本地 Excel 的能力；远程的 tool server 提供查天气、查地址等一组能力。
- 用一个**工具 client** 与工具 server 交互（类比 MySQL client、Redis client 与远程服务交互），client 与 server 保持**一对一**关系。

**为什么一对一（而非一对多）？** 理论上可以一对多，也有 Agent 框架的源码这么做；但 MCP 最终选一对一，因为更合理、好处更多：

- 职责清晰；
- 便于安全鉴权——不能让一个 client 畅通无阻访问所有人的服务；
- 各自保持独立的连接。

### 工具 server 内部可以很复杂

- server 里的工具不一定都是简单本地代码：第一个工具可能调 HTTP 接口，第二个调 WebSocket，第三个调 RPC 访问公司其他微服务……
- 本地 server 也一样：可能内部调 SDK、直接用本地代码，或调操作系统底层 API。

## 十、MCP 和 API 的区别（回答开篇疑问）

作者一开始也疑惑：MCP 说能让大模型"与万物互联"，这和调不同的 API 给大模型接入有什么区别？为什么要再搞一套协议？

理解：**MCP 无非是在已有的这些调用方式基础上又多包了一层**。

- 不管工具 server 内部怎么实现（HTTP / RPC / SDK / 本地代码），对外统一暴露一个接口（比如统一暴露成 HTTP）。
- 不光统一协议，还要统一交互的**数据格式**。
- HTTP 服务至少要提供两个功能：① 提供函数描述列表；② 能调用工具并返回结果。
- 所以 MCP 本质上就是在已有 API 基础上再包一层，用统一的 API 做统一实现。

> 借用玩笑话："著名的计算机科学家鲁迅曾经说过，在计算机的世界里，没有什么是加一个抽象层解决不了的问题。"（网络梗，非鲁迅原话）

### 为什么本地进程通信协议也要统一、为什么用 stdio

- 最初的目标是让大模型帮我们调工具做事，甚至**直接操作电脑**——帮我们写代码、传代码、发邮件等。
- 在大模型出现之前，这种"调一个接口就能做本地操作"的需求并不常见，常见的反而是网络请求（HTTP API / RPC）。所以需要一个全新的方案、架构、协议来解决"让大模型调工具"这个问题。

## 十一、MCP 的传输协议（重点）

### 1. 本地进程间通信：stdio

MCP 最终规定本地采用 **stdio 传输**。

**stdio 是什么**

- 最常见的底层机制是**管道**。
- 概念上指 standard IO，即进程的**标准输入 / 标准输出**接口。
- 操作系统中每个进程启动时，系统会分配三个文件描述符：
  - `stdin` 标准输入：默认是键盘；
  - `stdout` 标准输出：默认是屏幕；
  - `stderr` 标准错误。
- 代码里的 `printf` / `scanf` / `System.in` 等，都是通过这些标准输入输出接口与外界交换数据。

**管道是什么**

- 操作系统内核提供的一种进程间通信机制，能让一个进程的输出直接作为另一个进程的输入。

**stdio 传输**

- 通过标准输入和标准输出传递数据；这两个只是接口，中间用管道连接，一个进程的 stdout 直接传给另一个进程的 stdin，实现进程间通信，实际是一个**全双工通道**。
- 经典例子：`ps aux | grep python`——不用管道时 `ps aux` 的输出到屏幕；用管道后，它的 stdout 作为 `grep` 的 stdin，就能列出所有进程后过滤出包含 python 的进程。

**为什么在众多本地进程通信方式里选 stdio？** 本质原因是**它很简单**。MCP client / server 主要传输的就是 JSON，没必要像共享内存那样自己管理内存（共享内存是为了快）。

### 2. 远程服务接入：从 HTTP+SSE 到 Streamable HTTP

为什么不用 HTTP？看文档会发现它现在已经更新成 **Streamable HTTP**；但 2024 年 11 月最初是 **HTTP + SSE** 方案。先讲 HTTP+SSE 便于循序渐进理解。

**HTTP + SSE 怎么工作**

- 客户端发请求时，先用普通的 **HTTP POST**；
- 服务端响应通过 **SSE 通道**返回。
- SSE（Server-Sent Events）与普通 HTTP 的核心差异：**支持服务端主动发消息、流式推数据**。

**为什么选 SSE（根本原因）**

MCP 有一个重要需求：要能保证 **MCP server 向 MCP client 更新它的工具列表**——当 server 的工具发生变化时，需要给 client 发一条通知，client 收到后立刻再发请求拉取最新的工具列表。**这个"发通知"的能力必须通过服务端推送实现**。

另一个考虑：SSE 支持流式推送，比如拉很长的数据时能更及时地响应。

**Streamable HTTP（升级方案）**

HTTP+SSE 也不是最新方案，现在放着的是 Streamable HTTP。它其实是原方案的升级——不是一个标准协议名，而是指**基于 HTTP 协议的可流式传输技术**。相对 SSE 的优势：

1. **数据格式**：SSE 的 Content-Type 只能支持文本格式；Streamable HTTP 支持任意格式。
2. **跨平台兼容**：SSE 支持的客户端主要针对浏览器；Streamable HTTP 更通用。
3. **性能**更好。

**为什么有些 Agent 框架支持纯 HTTP 接入？** 作者的解释：

- 那种框架的 MCP client 是**随时用随时销毁**的（只是局部变量，没有全局维护），因此不存在"工具更新必须通知"的问题；
- MCP tool 绝大多数场景就是给一个 JSON，不需要多文本等数据，流式传输也不太必要；
- HTTP 大家都熟，所以就这么支持了。
- 这当然可以——只要你开发了一个 MCP server 托管平台、提供了接入入口，双方能对齐协议就 OK。

### 3. 经典架构图

学 MCP 时到处都能看到这张图：

- 一台电脑就是 **MCP host**，内部有多个 **MCP client**；
- 每个 client 与外部的一个 **MCP server 一对一**连接；
- 三条数据线表示三个 **remote MCP server**（远程），通过 **HTTP + SSE** 接入；
- 一条不太一样的线表示**本地启动的 MCP server**，用来访问电脑本地数据，通过 **stdio 传输**接入。

这就实现了前面说的**即插即用**：host 支持两种不同的接口，各种 server 都能接入。

## 十二、技术方案如何被 MCP 实现（回顾落地）

| 最初的技术需求 | MCP 的实现 |
|---|---|
| 工具与 AI 应用解耦 | 提出 C/S 架构，三个核心组成部分：**MCP host、MCP client、MCP server** |
| 通信协议统一 | 本地进程间通信 → **stdio**；远程 → **HTTP**（HTTP+SSE 或 Streamable HTTP） |
| 数据交换格式统一 | 基于 **JSON-RPC 2.0** 通信，所有消息都是 JSON 格式，方便解析、跨语言 |

### 三个核心组成部分

1. **MCP host**：就是 AI 应用程序（各种聊天网页、集成大模型的 IDE 如 Claude Desktop、Cursor、各种 Agent、普通前后端应用等）。
2. **MCP client**：本质上就是**实例化在 AI 应用程序后端内部的一个对象/实例**。官方文档例子：VS Code 作为 host，与一个 MCP server 建立连接时，运行期会实例化一个与之一一对应的 MCP client，由它负责获取工具信息、调用工具；要连另一个 server 时，再实例化另一个 client 对象维护连接。
3. **MCP server**：即工具服务。

### MCP server 至少要提供三个方法

1. `tools/list`：返回函数描述（工具列表）；
2. `tools/call`：执行方法；
3. `notifications/tools/list_changed`：服务端主动推送，告诉客户端工具有更新，让客户端再调用一次 `tools/list`。

这些接口的详细参数定义在官方文档里。看 Agent 框架源码点到 SDK 最底层，会发现它发起的最终网络请求体、收到的响应，就是严格遵循 MCP 协议规定的格式。

### 数据格式：JSON-RPC 2.0

所有通信消息都是 JSON 格式，方便解析、方便跨语言调用。

## 十三、接入工具的配置长什么样

作者找了一个 MCP server（高德地图），它同时提供基于 stdio 的本地接入配置和基于 SSE 的远程接入配置：

- **本地服务式（stdio）**：配置里新增一个叫 amap 的配置，本质是配置一条**命令行**：`command` 是 `npx`，还有 `args` 和环境变量。配好后，MCP host 执行这条命令；`npx` 用来执行 npm 拉到的包内部的可执行命令，于是把包启动起来，也就是启动一个本地 MCP server 服务（该服务同样实现了 MCP 协议规定的接口、方法，遵循数据格式要求）。
- **远程服务式（SSE）**：更简单，本质就是配置一个 **URL**。

**一句话总结**：本地接入配的是一条命令行，远程接入配的是一个 URL。

### TRAE 演示（字节的类 Cursor 本地 IDE，转录为"春意/吹意"）

- 在该 IDE 里添加 MCP server，就是帮你新增一条这样的配置；复制出来看，和上面高德地图提供的配置长得非常相似。
- 这正是 MCP 的伟大之处：**它把一切统一了**——不管是谁提供的配置都长这样，host 都能做标准化解析。
- 作者直接执行 npm 命令把配置的包拉下来：`npx` 是运行，`npm` 是只拉下来不运行。拉下来后 `node_modules` 里增加对应模块，然后执行其 bin 下对应的 JS 文件。
- **关键发现**：它并没有把 MCP server 的源代码拉下来，而是根据你的操作系统版本执行对应的**二进制文件**（这些二进制文件也作为包的一部分被拉下来）。这就解决了前面那个"企业不愿暴露源码又要提供本地能力"的问题。

## 十四、完整工作流程（基于 MCP 的 function calling）

1. **初始化**：因为是 C/S 架构，在对话之前（甚至可以在 AI 应用启动时）先完成初始化，发现服务端、保证它存活。MCP 协议规定了实现方式，过程类似 **TCP 三次握手**。
2. 初始化后，MCP client 向 MCP server 发起请求**获取工具列表**，并缓存到自己的内部字段里。
3. 用户发起自然语言提问，client 拿这个提问 + 内部缓存的可用工具列表去向大模型发起请求（这一套就是 function calling：用 system prompt 带工具列表，或用 API 参数带工具列表，都可以）。
4. 大模型给出调用指令后，AI 应用内部解析该指令，向 MCP server 发起一个标准请求——走 `tools/call` 接口。
5. MCP server 接到请求后，实际调用它的工具（工具内部可能请求第三方 API、实现本地方法、调 RPC 等，都不关心），然后封装标准化的返回结果给 AI 应用后端。
6. 后端带着用户原始输入 + 工具调用结果，向大模型发起**第二次请求**，大模型返回最终结果给用户。

## 十五、MCP 与 Function Calling 到底是什么关系

很多地方说或暗示二者是"技术递进"关系，**实际上不是**。

- **管的范围不同、互不干扰**：
  - function calling 主要强调 **AI 应用 ↔ 大模型** 交互的那部分（拿一个工具列表，返回一个文字版调用指令）；
  - MCP 只关心 **AI 应用 ↔ MCP server** 交互的那部分（如何拿到 function calling 所需的函数描述，如何根据返回的调用指令实现真正的工具调用）。
- **不在一个维度**：function calling 更倾向于是一种**能力**；MCP 更倾向于是一种**协议/规范、技术上的共同约定**。
- **不存在 MCP 取代 function calling**：即使有了 MCP，基于提示词的 function calling 和基于 API 的 function calling 都还在用、且将长期发展。作者观察一些 Agent 框架发现**基于提示词的 function calling 其实更常见**，猜想是因为基于 API 的方式外部依赖太高、无法自由切换模型。
- 如果看到"MCP 会取代 function calling"的说法，它想表达的更可能是：**MCP 会逐渐取代原有 function calling 实现流程中，把所有工具写死在 AI 应用本地、由开发者手动维护/开发工具、手动处理工具发现与调用逻辑的那套方案**。
- **结论**：MCP 是一个与 function calling **共存、服务于 function calling** 的新解决方案。

## 十六、如何更深入地学习 MCP

1. **看官方文档**：作者看了很多文档，觉得都没官方文档写得好。有语言困难就用浏览器一键翻译。
2. **带着"为什么"去读**：每看一部分都深入想"为什么要这样设计"。可以"格式化大脑"——假设眼前没有任何方案，自己会怎么设计，再对比自己想到的方案和最终方案的差异，学习优秀开发者的技术设计思路。
3. **动手写**：用官方 SDK 写一个 MCP server 并启动；再初始化一个后端应用、创建 MCP client，完成 client/server 之间完整的交互流程开发。
4. **看开源 Agent 框架源码**（作者强调这是关键）：
   - Agent 是最典型的 MCP host，追溯代码里所有涉及 MCP client / server 的逻辑。
   - client 一般通过 SDK 实例化，所以更重要的是 **SDK 内部实现**——要点到最里层，才能看到它最后怎么和 server 通信、发出什么消息。如果能找到，会看到它组装出特定格式的请求体。
   - 作者自己年初开始看 MCP，以为懂了；后来做了三个月 Agent 落地工作，发现其实什么都没理解。重看文档 + 大量源码（尤其 Agent 源码）后，才总算解答了最初的疑惑。

## 附：核心概念速查

| 概念 | 一句话解释 |
|---|---|
| Function calling（广义） | 让大模型调用外部工具的一类技术实现 |
| Function calling（狭义） | 大模型提供商在模型内部 + API 层做特别支持的能力（如 OpenAI 的 `functions` 参数） |
| 函数描述 | 方法列表及参数说明，用来告诉大模型有哪些工具可用 |
| MCP | Model Context Protocol，标准化应用程序向大语言模型提供上下文方式的开放协议 |
| MCP host / client / server | AI 应用 / 实例化在应用后端与 server 一对一通信的对象 / 工具服务 |
| tools/list / tools/call | 获取工具描述 / 执行工具调用 |
| notifications/tools/list_changed | 服务端推送通知，告知客户端工具列表有更新 |
| stdio | 本地进程间通信传输方式，基于标准输入输出 + 管道，因"简单"被选中 |
| HTTP+SSE | 早期远程传输方案：POST 发请求、SSE 通道返回，为支持服务端推送（工具更新通知） |
| Streamable HTTP | 现行远程传输方案，基于 HTTP 的可流式传输，支持任意 Content-Type、跨平台、性能更好 |
| JSON-RPC 2.0 | MCP 统一的数据交换格式，所有消息为 JSON，便于解析与跨语言 |
| 本地服务式 / 远程服务式接入 | 一条命令行配置拉包起本地进程 / 一个 URL 配置访问远程工具服务 |

01
Part One

Docker 容器

第一道坎 · 环境：把应用和它的运行环境打包成标准箱子，搬到哪都能跑。
是什么

容器 = 软件界的集装箱

传统部署像散装货物，环境靠人肉搬运；容器把代码 + 运行时 + 依赖 + 配置打包成标准化交付单元，交付过程标准化。

🚢 集装箱类比

货物不管里面装什么，集装箱尺寸统一，船、卡车、起重机都能处理。容器也一样：不管里面是 Node 还是 Python，Docker 引擎统一运行。

⚙️ 技术本质

容器是进程级隔离，共享宿主机内核，但拥有自己的文件系统、网络和进程空间。比虚拟机轻得多——秒级启动，MB 级体积。

关键点：容器不是迷你虚拟机。它不启动完整操作系统，所以快、小、密度高。
为什么用

它到底解决了什么痛点

✓ 环境一致

"在我机器上能跑"成为历史。开发、测试、生产用同一个镜像，杜绝环境差异导致的诡异 Bug。

⚡ 快速弹性

秒级启动与停止，配合编排工具可轻松水平扩容，资源利用率远高于虚拟机。

📦 可移植

一次构建，推到任意 Registry，在任意装有 Docker 的机器上运行——笔记本、服务器、云。

一句话：Docker 把"环境"变成了可版本化、可分发的代码。
核心概念

三个词，理解 Docker

▤ Image 镜像

只读的模板，包含运行应用所需的一切。分层存储，可复用。类似面向对象里的"类"。

▶ Container 容器

镜像运行起来的实例，有独立的可写层。类似"对象"。同一个镜像可以跑出多个容器。

📝 Dockerfile

用代码描述如何构建镜像的脚本。配合 docker build 生成镜像，让构建过程可复现。

深入 · 镜像

镜像不是一个文件，而是一叠层

镜像的分层存储基于 UnionFS：每一层只记录相对上一层的改动，最终联合挂载成一个文件系统。它更像一个虚拟概念，而非 ISO 那样的单个打包文件。

▤ 分层存储

Dockerfile 每一行都会新建一层。层一旦构建完成就不再改变，后一层对文件的增、删、改都只发生在自己这一层——删除文件也只是"遮盖"，不会真的缩小体积。

▶ 容器 = 镜像 + 可写层

镜像像"类"，容器像"实例"。容器运行时在镜像之上叠加一层可读写的容器存储层，对环境的修改只作用于这一层，不会污染镜像。

易失性：容器存储层的生命周期与容器一致——容器删除，其中的数据随之消失。要持久化，得用数据卷或绑定宿主目录（后面讲）。
深入 · 分发

仓库、Tag 与镜像的"全名"

Docker 用 Registry 存储和分发镜像：一个 Registry 下有多个仓库（Repository），每个仓库用标签（Tag）区分不同版本的镜像。

镜像命名规则 ubuntu # 等价于 ubuntu:latest（未指定标签默认 latest） ubuntu:24.04 # 官方仓库 ubuntu 的 24.04 版本 yyy/ubuntu:22.04 # 用户 yyy 在 Docker Hub 的 ubuntu 镜像 22.04 reg.example.com/team/app:v1 # 私有 Registry 上的镜像
规律：完整名字是 [registry/][用户/]镜像名:标签。省略用户名指向官方镜像，省略标签默认 latest。所谓"换源"换的就是默认 Registry（Docker Hub）的地址。
深入 · 命令

一条 docker run，背后做了四件事

看似简单的一条命令，其实串起了"找镜像 → 建容器 → 执行命令 → 终止容器"的完整流程：

1 找镜像

先查本地；没有就去 Registry（默认 Docker Hub）拉取到本机。

2 建容器

用准备好的镜像创建一个新容器并启动。

3 执行命令

运行你给的 command；没给就跑镜像里 CMD 指定的默认命令。

4 · 终止但不删除：命令执行完容器就停止了，但还在（docker ps -a 能看到）。加 --rm 才会跑完自动删。常用临时环境：docker run --rm -it ubuntu。
实操 · 命令

高频命令，照抄即用

终端 $ docker pull nginx # 拉取镜像 $ docker run -d -p 8080:80 --name web nginx # 后台运行并映射端口 $ docker ps # 查看运行中的容器 $ docker logs -f web # 实时看日志 $ docker exec -it web sh # 进入容器内部 $ docker stop web && docker rm web # 停止并删除 $ docker build -t myapp:1.0 . # 用 Dockerfile 构建镜像
-d 后台运行　-p 宿主:容器 端口映射　-it 交互式终端　--name 起个名方便管理。
实操 · Dockerfile

一个 Web 应用的典型构建

Dockerfile FROM node:20-alpine # 基础镜像，alpine 体积小 WORKDIR /app # 设定工作目录 COPY package*.json ./ # 先拷贝依赖清单 RUN npm ci --omit=dev # 安装生产依赖 COPY . . # 再拷贝源码（利用缓存） EXPOSE 3000 # 声明监听端口 CMD ["node", "index.js"] # 容器启动命令
分层缓存技巧：先 COPY 依赖清单再装依赖，源码改动时依赖层可复用，构建快很多。再加一个 .dockerignore 忽略 node_modules。
深入 · build

命令末尾那个 "." 到底是什么

很多人以为 . 是 Dockerfile 所在目录——不对。Dockerfile 由 -f 指定，而末尾这个路径是构建上下文。

$ docker build -f path/to/Dockerfile -t test:1.0 .

📦 上下文会整体上传

build 时，客户端把上下文目录下的所有内容打包发给 Docker Engine，引擎展开后才知道 COPY 要复制什么。所以 COPY 的源路径是相对于上下文的。

⛔ 超出上下文就拿不到

COPY ../a . 用了父目录文件、COPY /usr/x . 用了绝对路径——两者都超出上下文范围，构建必然失败。这也是为什么要配 .dockerignore 减小上传体积。

进阶 · 瘦身

多阶段构建：只把成品带走

编译完成后，源码和编译工具就成了累赘。多阶段构建让你在一个阶段编译，在另一个阶段只 COPY 成品，最终镜像不含依赖和源码。

Dockerfile FROM ubuntu AS builder WORKDIR /usr/src/cpp RUN apt update && apt install -y build-essential COPY main.cpp . RUN g++ main.cpp -o main -static FROM scratch COPY --from=builder /usr/src/cpp/main . CMD ["./main"]
关键词：AS 给阶段起名，COPY --from=builder 从上一阶段取文件（路径是镜像内的，不是宿主机的）。scratch 是空镜像；配合 -static 静态链接，最终镜像可小到 2.25 MB。
进阶 · 持久化

容器会消失，数据不能

数据卷是绕过联合文件系统的特殊目录：可在容器间共享、修改立即生效、更新不影响镜像，且不会随容器删除而消失。

$ docker volume create db # 创建数据卷 $ docker volume ls # 列出所有数据卷 $ docker run -d --name web \ --mount source=db,target=/app/data backend $ docker inspect web # 看 Mounts 字段确认挂载
另一种方式：绑定宿主目录——--mount type=bind,source=/abs/path,target=/app/data,readonly。本地路径必须用绝对路径；加 readonly 则容器内只读。两者都能让数据在容器重建后依然存在。
实操 · Compose

多容器编排：docker compose

一个 YAML 文件定义多个服务，一条命令拉起整个应用栈。

compose.yaml services: web: build: . ports: ["3000:3000"] depends_on: [db] db: image: postgres:16 environment: POSTGRES_PASSWORD: example
$ docker compose up -d # 一键启动所有服务 $ docker compose down # 一键停止并清理

Part Two

uv

第二道坎 · 依赖：一个工具替换 pip / virtualenv / poetry 的大半工作，而且快得离谱。
是什么

uv：Rust 打造的 Python 工具链

由 Astral（Ruff 的团队）用 Rust 编写。它既是包管理器，也是项目管理工具，目标是把 Python 生态里零散的工具统一起来。

10–100×
比 pip 安装更快
Rust
底层实现语言
All-in-one
安装 / 锁版本 / 建环境 / 管 Python
为什么这么快：Rust 编译型性能 + 并行下载 + 全局内容寻址缓存 + 高效的依赖解析。同一依赖只下载一次，多个项目共享。

实操 · 命令

从零开始的标准工作流

$ uv init myproject # 新建项目（生成 pyproject.toml） $ cd myproject $ uv add requests # 添加依赖，自动建虚拟环境+锁文件 $ uv add --dev pytest # 添加开发依赖 $ uv sync # 按锁文件同步环境 $ uv run python main.py # 在环境里运行，无需手动激活 $ uv python install 3.12 # 直接安装指定 Python 版本 $ uv tree # 查看依赖树
心智负担极低：不用手动 source activate，uv run 自动找到环境。装完依赖自动生成 uv.lock 保证可复现。
实操 · 项目文件

pyproject.toml 长什么样

pyproject.toml [project] name = "myproject" version = "0.1.0" requires-python = ">=3.11" dependencies = [ "requests>=2.31", "pytest>=8.0; extra == 'dev'", ]
# 兼容 pip 的用法：直接编译 / 安装 requirements $ uv pip compile pyproject.toml -o requirements.txt $ uv pip sync requirements.txt
迁移成本低：uv 完全拥抱标准 pyproject.toml，也提供 uv pip 接口兼容 requirements.txt 老工作流。

Part Three

MCP

第三道坎 · 连接：Model Context Protocol——让 AI 安全、标准地连上外部工具与数据。
是什么

AI 世界的 USB-C

USB-C 统一了设备连接；MCP 统一了 AI 应用 与 外部能力 的连接方式。它由 Anthropic 于 2024 年开源，是一套开放标准。

🔌 标准化接口

过去每个 AI 应用要为每个工具单独写适配。MCP 定义统一协议，工具只需实现一次，任何支持 MCP 的客户端都能用。

🌐 生态可复用

文件系统、GitHub、数据库、Slack……社区已有大量现成 Server，拿来即用，也能自己写。

解决的核心问题：让大模型从"只会聊天"变成能调用工具、读取实时数据、执行操作的助手。

深入 · 关系

Function Calling 和 MCP，到底是什么关系

这是最容易被讲混的一点。Function Calling 是模型的能力，让 LLM 能"提出要调用某个函数"；MCP 是协议的规范，规定工具怎么被描述、注册、发现、调用。

🧠 Function Calling（模型侧）

模型根据函数描述，输出结构化调用请求（要调哪个函数、参数是什么）。分两层：模型层学会"何时调"，API 层用 tools 字段把函数描述传给模型。它不负责真正执行。

🔌 MCP（协议侧）

解决"工具如何被广泛复用"：统一 Server 的注册、工具发现（tools/list）、调用（tools/call）与结果回传格式。任何支持 MCP 的客户端都能直接消费同一个 Server。

一句话区分：Function Calling 让模型会提出调用；MCP 让工具能被统一地接进来——前者是能力，后者是标准。基于 MCP 的调用，本质就是"用 MCP 工具描述驱动的 Function Calling"。
深入 · 传输

三种传输方式：一条演进线

传输方式解决的是"client 和 server 怎么说话"。记住演进顺序，就不会被过时资料带偏：

1 stdio（本地）

标准输入输出 + 管道，按行分隔 JSON-RPC。配置就是一条命令（command + args），本地首选。

2 HTTP+SSE（已废弃）

初代远程方案：POST 发请求 + SSE 通道回消息，需维护两个端点。已被官方标为 deprecated，仅为兼容保留。

3 Streamable HTTP（现行）

单一端点同时支持 POST/GET，SSE 变成按需的流式响应。支持断线续传、会话管理，跨平台更好。

为什么改：SSE 只能传文本、主要面向浏览器、要维护两个端点；Streamable HTTP 收敛为一个 URL，支持任意 Content-Type 与断线重连。配置形态仍是 { "url": "https://…/mcp" }。
实操 · 接入现成 Server

5 分钟给 AI 装上能力

在客户端配置里声明 MCP Server，重启即可。以文件系统 Server 为例：

claude_desktop_config.json { "mcpServers": { "filesystem": { "command": "npx", "args": [ "-y", "@modelcontextprotocol/server-filesystem", "/path/to/allowed" ] } } }
安全提示：Server 的权限由你授予。filesystem Server 只能访问配置里指定的目录——按需授权，最小权限原则。
实操 · 手写一个 Server

一个工具，十几行代码

server.py（基于 FastMCP） from mcp.server.fastmcp import FastMCP mcp = FastMCP("demo") @mcp.tool() def add(a: int, b: int) -> int: """两数相加""" return a + b if __name__ == "__main__": mcp.run() # 默认用 stdio 传输
$ pip install mcp # 或用 uv add mcp $ python server.py # 在支持的客户端里配置启动
只需加装饰器 @mcp.tool()，函数的类型注解和 docstring 会自动变成工具的描述。把脚本路径配到客户端的 mcpServers 里即可调用。
